# 知识库P0修复：接入与验收说明

本轮处理知识库的三个工程问题：全库命中后可按ID读取；法规按主体、产品、环节保守选择并保留全文和例外；同一输入的多个候选机制不再截断为两个。Agent的检索循环、追问与最终判别仍由应用层负责。

## 本轮提供什么

- 9639份文书、110878个读取单元的只读消费索引；沿用原稳定ID、候选、来源坐标和五项版本。
- 67条法规范围侧表；12份已有机制指南及其来源和边界标记。
- 范围选择、法规及上下文整组装配、多风险阅读覆盖提示。
- 独立编制、另行模型复核的36条合成营销／培训输入和参考。18开发、18留出；24主分析、12边界挑战，尚未执行新模型效果测评。

消费索引用于回读现有检索命中的内容。BM25与BGE双路初召回、1:1 RRF融合、DeepSeek重排沿用既有方案，本轮没有改变排名或新增其效果指标。

## 给应用开发者的接口

从交付根目录的`code`导入`EvidenceRuntime`，显式传入交付目录和`contracts/runtime_manifest.json`的可信SHA256。该指纹见同目录`runtime_lock.json`；正式部署应由应用配置固定，不应从不可信下载内容自动信任。

```python
from evidence_runtime import EvidenceRuntime

# root及pin由部署配置传入。每进程保留一个实例。
with EvidenceRuntime(root, pin) as kb:
    result = kb.read_case(retrieval_hit_unit_id, layer="hit")
    bundle = kb.get_evidence_bundle(
        ["M02"], [retrieval_hit_unit_id],
        current_text=business_text, scope_facts=scope_facts,
        budget_chars=8000,
    )
```

工具操作包括`list_mechanisms`、`read_mechanism`、`read_article`、`read_case`、`read_span`、`get_dependencies`、`get_coverage`、`get_input_coverage`、`get_evidence_bundle`。ID须来自已登记目录或检索结果。原`coverage`名称和`law_and_guide_text`字段保留兼容别名。

也可运行`code/runtime_cli.py --root <交付目录> --pin <可信指纹> serve`保持本地JSONL工作进程。每行请求严格为`{"operation":"read_case","arguments":{"unit_id":"已登记ID"}}`。当前入口串行处理；并发应用应按工作进程保留独立实例。工作进程只读本地资料，不调用模型；这不是已部署的MCP服务。

## 范围信息如何传入

范围事实格式为`{"product":{"value":"investment_linked","origin":"current_input","quote":"投资连结型保险","start":17,"end":24}}`，坐标须以实际输入重新计算；上述数字仅示意格式。

主体`actor`、产品`product`、环节`stage`均可缺省。引用必须来自当前输入，工具只机械核对原句，**不证明调用方的语义分类正确**。身份归属、多个产品、混合行为或事实不清时应保留unknown，或按明确对象分别装配。

范围不匹配仅排除本次直接规范装配，原条文始终可按ID补读。general/unknown轴不构成排除依据。其他轴只有直接原文依据且枚举支持互斥时才排除；解释轴不作确定排除。环节标签包含时间、渠道和义务类型，彼此可能重叠，本版不因不同环节值直接排除条文。

已修补第29条主体枚举，保留一般书面受托确认分支；没有把非本人确认一概认定为违规。公司与代理机构、万能险与投连险仍须分别核实。

## 如何使用证据包

送入模型的两个文本字段为`case_text`和`legal_assembly.text`；兼容字段`law_and_guide_text`与后者相同，不要重复发送。总预算按这两个字符串的Unicode字符数相加计算；其他结构化字段用于核验与追溯，不是额外事实证据。

法规及登记的必要上下文优先，正文与例外不截断，来源说明按来源去重。超预算时整组省略，并返回`next_read_article_ids`、`next_read_case_unit_ids`和partial状态。已由其他根条装入的内容不再列为待补读。应用应按需要补读，不能把未展示当成无风险。

`get_input_coverage`提供阅读候选、原句触发、已读、调用方声称已检查及未检查列表。它不是风险分类器，未处理否定、真实授权、合同内外或归责。已读不等于已判，词表无触发不等于安全；任何返回都不证明整段无风险。当前12机制没有完整覆盖官方27标签。

## 已验证与尚待验证

工程验证报告放在`reports`，全库读取验证放在`full_reader/bundle_v2`。7个已知失败探针比较旧、新材料装配，不能据此声称召回率或风险判别准确率提高。旧实验结果保持原口径。

新36题用于后续验证。只给模型单条匿名输入，每题新上下文；不发送参考、原题号、分组或顺序标签。只用开发题调试，配置冻结后再运行留出。12条边界待定参考单列挑战结果，不混入24条主分析。参考属于模型银标，尚非人工／金融专家金标。

未完成：新题的实际DeepSeek判别与检索测评、全库完整相关集及真实全库Recall、法规原始HTML/PDF字节归档与全部历史时效核定、其余标签覆盖和全量语义审核、自动增量重建与线上服务部署。RAPTOR与GraphRAG未纳入本轮。

## 性能与部署

SQLite数据库约600MB，保存原始记录及可回读区间，不常驻解码全库。启动时校验文件指纹并完整流式核对记录，冷启动为分钟级；须每进程初始化一次并保持实例，不能每次工具调用重新启动。单次读取实测见性能报告。8MiB指的是共享JSON字节缓存上限，另有4MiB SQLite页缓存；未测全进程RSS，不能据此宣称总内存只有12MiB。

文件可移动使用，运行时不回退到原工作目录。数据库只读，不创建WAL等写入副作用。便携测试通过后记录在`reports/portable_verification.json`。本轮没有自动替换应用默认版本或更新GitHub。
